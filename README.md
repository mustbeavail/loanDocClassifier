# 대출 서류 PDF 페이지 분류기

여러 종류의 대출 서류가 무작위로 섞인 PDF를 입력받아, 페이지마다 문서 유형을 판별하고 같은 문서끼리 다시 묶습니다.

라벨: `URLA_1003` / `INCOME_DOC` / `CREDIT_REPORT` / `TITLE_REPORT` / `OTHER`

---

## 1. 실행 방법

Java 21, Node.js 20.9 이상. 그 밖에 설치할 것은 없습니다(윈도우 기준). macOS·Linux는 Tesseract를 따로 설치해야 합니다.

```
cd backend   →  mvnw.cmd spring-boot:run      (macOS·Linux는 ./mvnw spring-boot:run)
cd frontend  →  npm install && npm run dev
```

브라우저에서 `http://localhost:3000`. 탭은 셋입니다.

- **분류하기** — PDF를 올려 판정과 그룹핑을 봅니다. 정답지 대조를 켜면 그 자리에서 정확도를 잽니다. **Gemini 키가 필요합니다.**
- **저장된 결과** — 두 패키지의 분류·그룹핑 결과를 미리 산출해 커밋해 둔 파일에서 읽습니다. **제공 자료도 키도 없이 볼 수 있습니다.**
- **저장된 정확도** — package_01 정답지와의 대조표를 읽습니다. 역시 자료·키가 필요 없습니다.

**Gemini API 키** — 없어도 실행됩니다. 다만 규칙으로 풀리는 만큼만 나오고 나머지는 미판정으로 남습니다. 전체 결과를 보려면 `backend/src/main/resources/application-local.properties`를 만들고 `gemini.api-key=키` 한 줄을 넣으십시오(키는 제출 메일에 첨부). 환경변수 `GOOGLE_API_KEY`도 됩니다.

## 2. 문제 정의

셋으로 쪼갰습니다. **① 페이지 읽기 → ② 페이지 분류 → ③ 문서 그룹핑.**

**핵심 가정은 ③이 단순 병합이 아니라는 것입니다.** 제공 PDF는 문서가 아니라 **페이지 단위로** 섞여 있습니다. package_01에서 대출신청서 11장은 2·4·6·10·14·20·24·26·30·35·38쪽에 흩어져 있습니다. 인접한 같은 라벨을 잇는 방식으로는 풀리지 않습니다.

그래서 **라벨 + 페이지에 인쇄된 마커(`N of M`)로 원래 문서를 재조립**하는 문제로 정의했습니다. 순서는 뒤섞였어도 종이에 찍힌 순번은 그대로 남아 있기 때문입니다.

## 3. 기술 선택과 근거

| 선택 | 이유 |
| --- | --- |
| **Java + Spring Boot** | 언어 제한이 따로 없었고 제 주력 스택이기 때문에 선택했습니다. PDF·OCR·LLM 모두 자바 라이브러리가 있습니다 |
| **JavaScript + Next.js** | 결과표·라벨 색 띠·혼동행렬을 브라우저로 보여 주기 위함 |
| **Apache PDFBox** | 텍스트 추출과 스캔 페이지 렌더링을 한 라이브러리로 처리 |
| **Tesseract OCR** (Tess4J) | 로컬 실행이라 페이지가 늘어도 비용이 0이고, 같은 입력에 같은 결과가 나와 정확도 측정이 재현됩니다 |
| **Google Gemini API** (`google-genai`) | 규칙으로 안 되는 것만 담당. **상용 API 사용에 해당합니다** |

**AI를 단계별 역할에 맞게 나눠 붙였습니다.** 스캔 페이지를 글자로 바꾸는 일은 판단이 개입하지 않으므로 가장 싸고 결정적인 **OCR**에, 처음 보는 양식을 문맥으로 유추해야 하는 2차 판정과 그룹핑은 **LLM**에 맡겼습니다. 개발 과정에는 **코딩 에이전트(Claude Code)** 를 썼습니다.

### 검토했지만 선택하지 않은 것

- **전 페이지를 LLM 비전으로 처리** — 정확도는 가장 높겠지만 규칙으로 100% 잡히는 페이지까지 비용을 태웁니다. 대량 처리에서 확장성이 나쁩니다.
- **OCR 없이 스캔 페이지도 LLM 비전으로** — 페이지 수에 비례해 비용이 늘고 응답이 비결정적이라 정확도 측정이 재현되지 않습니다. "글자만 읽으면 되는 일"에 LLM을 쓸 이유가 없다고 봤습니다.
- **직접 학습한 ML 분류기** — 학습 데이터가 39페이지이고 그중 소득증빙은 1장입니다. 과적합이 확실합니다.
- **레이아웃 기반 문서 AI(LayoutLM 등)** — 자바 생태계에서 다루기 어렵고 마감까지 검증할 시간이 없었습니다.

## 4. 처리 흐름

```
PDF → [1] 페이지별 텍스트 추출
    → [2] 텍스트가 비었고 이미지가 있으면 OCR
    → [3] 규칙으로 1차 분류
    → [4] 규칙이 보류한 페이지만 LLM 2차 판정
    → [5] 라벨 + 페이지 마커로 그룹핑 (부족하면 LLM)
```

뒤 단계일수록(LLM) 느리고 비쌉니다. 앞 단계가 답을 낸 페이지는 넘기지 않습니다.

**[2] OCR은 조건부** — 텍스트 레이어를 먼저 읽고, **텍스트 레이어가 비어 있으면서 이미지가 있는** 페이지만 렌더링합니다. 스캔 페이지가 회전되어 있는 경우가 있어, 방향을 돌려 가며 읽어 보고 인식 신뢰도가 기준을 넘는 방향을 채택합니다.

**[3] 규칙은 문서 유형 고유 문자열에만 겁니다.** 발행사명에 걸면 발행사가 바뀔 때 **오분류**가 납니다. 유형 문자열에 걸면 **미발화**로 끝나 2차로 넘어갑니다. 틀린 답보다 답을 안 내는 쪽이 안전합니다.

| 라벨 | 키워드 |
| --- | --- |
| `URLA_1003` | Freddie Mac Form 65 / Fannie Mae Form 1003 / Uniform Residential Loan Application |
| `CREDIT_REPORT` | Repositories: TUC/EXP/EQX / Credit Score Disclosure |
| `TITLE_REPORT` | Preliminary Report / Commitment for Title Insurance / COMMITMENT CONDITIONS |
| `INCOME_DOC` | Wage and Income Transcript / Form W-2 / Sensitive Taxpayer Data |

권원보고서 키워드가 셋인 이유는 같은 라벨이라도 지역과 문서에 따라 양식 이름이 갈리기 때문입니다(package_01은 캘리포니아식 `Preliminary Report`, package_02는 `ALTA Commitment`).

후보 문자열을 39페이지 전부에 대입해 **한 라벨에만 걸리는 것**만 채택했습니다. `credit report`·`credit score`는 신청서에도, `escrow`는 권원보고서와 신청서 양쪽에 나와서 뺐습니다. 발행사명(XACTUS 등)은 이 묶음에서는 잘 맞지만 위 이유로 뺐습니다. 키워드를 더 넣으면 보류를 줄일 수 있었지만, 제공된 39페이지에만 맞는 규칙이 되므로 넣지 않았습니다.

`OTHER`는 규칙에 넣지 않았습니다. "나머지 전부"를 뜻하는 긍정 키워드가 없기 때문입니다. LLM 응답 라벨에만 두었습니다.

**[5] 그룹핑** — 같은 라벨을 모아 놓고 봅니다.

1. 페이지 마커 규칙(`N of M`, `Page N of M`, `PAGE N OF M`, 총장수 없이 쪽번호만 찍는 `Page N`)으로 1차로 순서를 정합니다.
2. 규칙에 없는 새 표기이거나 마커 자체가 없으면 LLM이 판정합니다. 같은 양식이 여러 벌이라 순번이 겹칠 때도 마찬가지입니다.

페이지 마커 규칙에 걸리지 않는 문서들은 LLM으로 넘기는데, 리포트아이디·파일 번호·문서 번호 등으로 명백히 하나의 문서로 묶이는 문서임에도 LLM이 별도 문서로 그룹핑하는 문제가 있었습니다. 그래서 기타 설득력이 낮은 식별자들보다 위 식별자들의 우선순위를 높게 가져가도록 프롬프트를 작성해 하나의 문서로 그룹핑하도록 했습니다. 그 후에 LLM이 pdf 내용을 기준으로 순서를 판단하게 했습니다.

에이전트에게 판단을 맡겼더니 package_01 정답지에 맞도록 그룹핑 프롬프트에 지엽적인 조건을 덧붙이는 경향이 있었습니다. 근거 없이는 묶지 않도록 고쳤고, 그 대가로 완벽한 그룹핑을 포기했습니다. package_01 기준으로 39장 중 2장을 못 맞춥니다. 도면 1장은 미분류, 신용보고서 표지 1장은 자리가 틀립니다.

## 5. package_01 정확도

**측정 방법이 이 항목의 핵심입니다.** 원본 4개 문서와 셔플본의 페이지 텍스트를 대조해 코드로 자동 생성했고, 39페이지 전부 1:1로 매칭됐습니다(미매칭 0). 같은 명령을 다시 돌리면 같은 정답지가 나옵니다.

```
mvnw.cmd test -Dtest=GroundTruthGeneratorTest -DtestPdfDir="자료 폴더 경로"   # 정답지 재생성
mvnw.cmd test -Dtest=RuleAndLlmAccuracyTest   -DtestPdfDir="..."            # 정확도 재측정 (키 필요)
mvnw.cmd test -Dtest=Package01GroupingTest    -DtestPdfDir="..."            # 그룹핑만 재측정 (키 필요)
mvnw.cmd test -Dtest=Package01ResultTest      -DtestPdfDir="..."            # 저장된 결과 재생성 (키 필요)
mvnw.cmd test -Dtest=Package02ResultTest      -DtestPdfDir="..."            # package_02 결과 재생성 (키 필요)
```

| 단계 | 정확도 | 보류 | 오분류 |
| --- | --- | --- | --- |
| 규칙 단독 | 32/39 = **82.1%** | 7장 | 0장 |
| 규칙 + LLM | 39/39 = **100%** | 0장 | 0장 |

| 라벨 (규칙 단독) | 정답 | 판정 | 정밀도 | 재현율 | F1 |

| `URLA_1003` | 11 | 11 | 1.000 | 1.000 | 1.000 |
| `CREDIT_REPORT` | 18 | 13 | 1.000 | 0.722 | 0.839 |
| `TITLE_REPORT` | 9 | 8 | 1.000 | 0.889 | 0.941 |
| `INCOME_DOC` | 1 | 0 | 0.000 | 0.000 | 0.000 |

### 규칙이 보류한 7장

| 페이지 | 정답 | 놓친 이유 |
| --- | --- | --- |
| p3·p13·p23·p29 | `CREDIT_REPORT` | 신용조회사가 별도 레터헤드로 발행한 통지문·소명 요청서. 본문에 찍히는 헤더가 없습니다 |
| p17 | `CREDIT_REPORT` | 대주가 직접 발행한 신용점수 고지문. 조회사 헤더가 아예 없습니다 |
| p8 | `TITLE_REPORT` | 도면 위주라 읽을 글자가 82자뿐입니다 |
| p36 | `INCOME_DOC` | 손익계산서. 채택한 소득 키워드는 W-2·세무기록 계열이라 걸리지 않습니다 |

규칙을 유형 고유 문자열에 건 대가가 여기서 드러납니다. 본문 양식에서 벗어난 페이지는 규칙이 잡지 못하고, 그 자리를 LLM이 메웠습니다.

## 7. 한계와 개선 방향

**1. LLM 그룹핑에서 표지 순서를 맞추지 못하고, 도면은 항상 미분류입니다.**

**2. `OTHER`를 시험해보지 못했습니다.** 제공된 두 패키지에 해당 페이지가 한 장도 없습니다.

**3. 검증 자료가 패키지 둘뿐입니다.** 다른 발행사 양식에는 규칙이 안 통할 가능성이 높고, 소득증빙은 형태 편차가 가장 큰데 정답지 있는 샘플이 1장뿐입니다.

**4. 페이지가 수백 장으로 늘면** 한 라벨의 페이지를 한 프롬프트에 다 넣지 못합니다. 실무 적용 시 먼저 손봐야 할 지점입니다.

**5. LLM 판정의 재현성을 충분히 검증하지 못했습니다.** 온도를 0으로 두었지만 같은 입력에 같은 결과가 나오는지는 몇 차례 돌려 본 수준입니다. 반복 횟수가 적어 어느 정도 흔들리는지 수치로 말할 수 없습니다.
